# 0.3.13：普通文档输入的句间续写

2026-09-22。用户指出手动句号后仍不续写并明确要求继续修复。本轮在0.3.12既有未提交改动上进行局部修改，没有提交、推送或改变其他项目输出。

## 修复范围

句号本身不被结构门拦截；此前新增的文档续写指令仅存在于已确认Tab接受的分支，手动输入仍走普通模板。现将句间策略设为所有远程文档末尾请求的共同策略，普通和接受后共用。接受后只追加真实阶段说明，不再重复原先更强的停笔限制；不伪造接受状态。聊天、中间插入、本地模型模板及请求/显示/接受身份保护、调度与超时维持原行为。

新策略区分一句完成和段落结束，允许说明已有条件、动作、结果之间的直接关系；业务范围的只/仅不自动意味着禁止解释，作者明确限制本段输出或只有待定内容时仍停笔。不新增原文未说明的业务事实；不以盲重试、固定补句或放宽过滤提高输出率。

## 语义验证与残余问题

全部为固定合成文本，不保存截图的真实业务原文。三版各6组旧/新配对，共36次联网；最终生产协议/客户端另6次，共42次。探针进程内读取已有凭据，不输出或保存Key。

第一、二版否决：两分支价格规则出现原文未说明的价格变化行为，第二版甚至将两个分支错误概括为相同结果。第三版加入不涉及业务对象的判断示例后，最终生产客户端对同一两分支句号规则3次独立请求均生成“前一次是否结束是区分取值方式的依据”，每次2.08–2.39秒。普通说明1例有自然续句；作者明确范围、只有缺参数各1例为空。6次全部HTTP200、普通阶段，无缓存命中。

这证明普通句号模式确实使用新契约，并能在这组规则上生成有依据的关系说明；不证明所有句号都必须有输出，也不证明整体空结果率下降。最后一轮配对仍有未介绍的限时任务被推定使用独立任务池、补寄状态被称为唯一依据等反例；这些不能列为正确结果，业务语义可靠性仍未全面解决。提示词不是形式化规则校验。
