# ADR-0005：表达加密落盘，运行时内存检索

## 状态

接受

## 背景

阶段 2 需要从本地聊天中生成常用表达并实时检索。原始聊天已经使用应用层加密，但普通 FTS5 必须把表达或分词以明文写入 SQLite；常用表达本身可能包含项目信息，不能因为它是派生数据就降低保护标准。

第一版是单用户 macOS 工具，预计有效表达远少于原始消息。用户要求先简单实现功能，暂不为语义检索和极端规模增加依赖。

## 决策

- 表达正文继续使用现有 Encrypt-then-MAC 信封加密后写入 SQLite。
- SQLite 只额外保存带密钥的表达摘要，用于去重和删除墓碑；摘要不参与前缀搜索。
- 应用在一次成功扫描和表达重建后，把有效表达解密到进程内存，建立不可持久化的前缀检索结构。
- 应用退出后不保存内存索引；下次启动只有在用户已经建立本地资料库后才重新加载。
- 第一版不使用 FTS5、SQLCipher、向量数据库或持久化盲索引。

## 后果

### 正面

- 磁盘、SQLite、WAL、SHM 和日志中不出现表达明文。
- 沿用现有密钥、加密信封和数据库，不增加第三方依赖或迁移工具。
- 对个人规模的固定短语前缀匹配足够简单，容易验证和重建。

### 负面

- 启动或重建后需要解密有效表达并占用少量内存。
- 第一版只适合前缀匹配，不能提供真正的语义近义搜索。
- 进程运行期间表达以普通字符串存在于本机内存；当前威胁模型不抵御已取得同一用户进程调试权限的恶意软件。

## 替代方案

- **明文 FTS5：** 开发最简单，但会让表达明文落盘，拒绝。
- **SQLCipher：** 可以在整库加密后使用 FTS5，但新增二进制依赖、签名和迁移成本，留到真实规模证明需要时再评估。
- **持久化 HMAC 盲索引：** 不泄露原文，但需要大量前缀／n-gram 记录和更复杂的密钥轮换，第一版不采用。
