# 阶段 1 批次 B 安全审计

日期：2026-08-20

## 结论

本批次没有发现 Critical 或 High 风险。合成测试证明消息正文和工作目录以加密信封写入 SQLite，主密钥只进入 macOS Keychain，SQL 全部使用参数绑定；Task 7 进一步验证消息与游标原子提交、增量恢复和只新建 staging 数据库，但当前仍未授权导入真实历史。

## Critical

无。

## High

无。

## Medium

1. **主密钥轮换尚未实现**
   - 影响：长期使用后无法主动更换数据库主密钥。
   - 后续：在正式导入真实历史前设计事务式 rekey；失败时保留原数据库和原 Key。

2. **SQLite 元数据未整体加密**
   - 影响：数据库单独泄露时仍可看到记录数量、时间、角色、字符数和随机 thread/message ID；正文与工作目录不可见。
   - 当前判断：第一版本地单用户工具可接受，但 UI 不应宣称“整库完全不可识别”。
   - 后续：若引入 SQLCipher，按 ADR 迁移；否则评估对外部 ID 做带密钥的稳定映射。

3. **脱敏规则不可能证明覆盖所有未知秘密格式**
   - 影响：阶段 3 远程补全若直接复用单次脱敏，未知格式可能漏传。
   - 后续：本地入库前和远程发送前各扫描一次；远程请求采用字段白名单，并提供“本次发送的数据类型”预览。

## Low

1. **Schema 同时存在 SQL 文件和内嵌常量**
   - 影响：后续修改可能漂移。
   - 当前：Task 7 已增加 v1→v2 自动迁移测试，但两份 schema 定义仍然存在。
   - 后续：应用打包时改为单一 schema 资源或构建期生成。

2. **本地来源路径仍存在同用户竞态边界**
   - 影响：拥有同一 macOS 用户权限的另一个进程可在扫描前改写 `~/.codex` 下的普通文件；这类进程本身也已拥有读取历史的能力。
   - 当前：拒绝符号链接，读取前后核对 device/inode/size，下次导入按 thread ID、inode、偏移和绝对行号恢复；元数据重放不一致会失败。
   - 后续：常驻应用只接受规范化后的固定 Codex 根目录，来源变化时丢弃本次结果并重试，不允许 UI 传入任意文件路径。

## 已执行证据

- `make data-core-test`：行读取、记录解析、来源扫描、8 类脱敏、加密信封、钥匙串、SQLite 幂等测试全部通过。
- 加密测试：随机 IV、正确密钥往返、错误密钥失败、密文单字节篡改失败。
- 跨进程钥匙串：`create=true`、`verify=true`、`delete=true`，未输出密钥内容。
- SQLite：同一来源导入 3 次仅首次新增；SQL 注入样本作为普通字符串保存；数据库文件中未检出合成 Key、邮箱和工作目录；权限为 `0600`。
- 增量恢复：半行、重启、重复扫描、截断、inode 更换、active→archived 与失败事务回滚均通过；失败事务中消息和游标都未残留。
- Schema：v1 数据库打开后自动增加 device、inode 和绝对行号字段，迁移测试通过。
- 重建：合成 root＋subagent 来源只导入 4 条 root 可见消息；已存在目标返回 2 且内容不变；非 staging 后缀不创建文件。
- Clang 静态分析：`Sources/CodexDataCore/*.m` 无告警。
- 源码扫描：未检出完整 Key 形态或用户接口地址。
