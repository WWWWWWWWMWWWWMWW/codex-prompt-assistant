# 阶段 2：简化版动态表达库设计

日期：2026-08-20
状态：用户已确认“第一版先简单实现功能，后续迭代”

## 1. 第一版结果

用户完成一次 Codex 历史扫描后，应用自动从本地加密资料库中找出重复出现的用户句子，生成加密常用表达库。用户在 Codex 输入框输入表达前缀并停顿 650ms 后，现有候选条显示剩余文字；`Tab` 插入剩余部分，`Esc` 关闭。

没有匹配时不显示候选条，不再用阶段 0 固定测试文案冒充智能建议。整个阶段只做本地建议，不调用远程接口。

## 2. 第一版只做什么

- 只学习 `user` 消息，不学习 AI 回复。
- 按换行和中文／英文句末标点切分完整句子。
- 只保留 4～160 个字符的自然语言句子。
- 同一规范句必须在至少两个不同会话中出现，才成为有效表达。
- 去重只处理首尾空白、连续空白和统一换行，不做近义合并或模板变量识别。
- 排名只看跨会话次数、总次数和最近出现时间。
- 扫描成功后自动完整重建派生表达库；重建失败时保留上一次可用表达和内存索引。
- 表达正文加密落盘，运行时只把有效表达解密到内存做前缀匹配。
- 表达删除写入墓碑；完整重建后不得恢复。

## 3. 第一版明确不做

- AI 回复学习、用户采用判断和接受／拒绝权重学习。
- 可变模板、近义表达合并、项目／场景权重和时间衰减。
- FTS5、SQLCipher、向量模型、本地生成模型和语义搜索。
- Codex 目录实时监听；第一版在用户执行数据扫描后自动更新表达库。
- ChatGPT 桌面实时采集和远程智能续写。
- 表达管理窗口；核心删除／墓碑 API 先实现并验收，管理 UI 后续补。

## 4. 低保真流程

```text
用户点击“扫描并导入 Codex 历史”
                │
                ▼
      阶段 1 增量导入完成
                │
                ▼
  流式解密 user 消息，不打印正文
                │
                ▼
  分句 → 排除代码／秘密／噪声 → 规范化
                │
                ▼
  至少跨两个会话重复？ ──否──→ 不进入表达库
                │是
                ▼
      加密写入表达与来源关系
                │
                ▼
   解密有效表达，替换内存前缀索引
                │
                ▼
用户输入“先别急着” → 显示“做，先把方案梳理清楚”
```

## 5. 数据模型

在同一个 SQLite 中增加四类派生数据：

- `expressions`：带密钥摘要、加密正文、出现次数、跨会话次数、最近时间和抽取器版本。
- `expression_occurrences`：表达与原始消息的来源关系；原始消息删除时级联删除来源关系。
- `expression_tombstones`：用户屏蔽表达的带密钥摘要和加密展示文本；重建时先排除。
- `expression_builds`：构建版本、状态、输入消息数、有效表达数和耗时，只记录计数。

原始 `messages` 仍是唯一事实来源。表达表全部可以删除重建，但墓碑必须保留。表达摘要只用于确定“是不是同一句”和阻止复活，不承担搜索功能。

## 6. 抽取规则

第一版采取保守规则：

1. 只读取角色为 `user` 的消息。
2. 消息已有敏感信息命中记录时，整条消息不参与学习。
3. 包含代码围栏、URL、明显文件路径、JSON／日志结构或高比例程序符号的片段不参与学习。
4. 片段按换行、`。！？!?；;` 切分；清理首尾和重复空白。
5. 长度小于 4 或大于 160 的片段排除。
6. 同一会话重复多次只增加总次数，不能单独满足“跨两个会话”。
7. 达到两个会话后才写入有效表达库。

宁可第一版建议少，也不把代码、秘密或一次性内容学进去。

## 7. 内存建议规则

- 只在光标没有选中文字时查询。
- 取光标前最后一个换行或句末标点之后的文本作为当前片段。
- 中文至少输入 3 个字符，纯 ASCII 至少输入 3 个字符才查询；“但是／而且／然后”等通用连接词还需再输入至少 3 个字符，避免短前缀命中无关历史表达。
- 候选完整表达必须严格以当前片段开头，插入内容只是尚未输入的后半段。
- 多个候选按跨会话次数、总次数、最近时间排序，只显示第一条。
- 内存索引为空、正在重建、输入法组词中或没有匹配时不显示。
- 日志只记录候选数量、建议长度和耗时，不记录当前输入或表达正文。

## 8. 失败与恢复

| 情况 | 行为 |
| --- | --- |
| 原始数据扫描部分失败 | 不启动表达重建，继续使用上一次索引 |
| 某条消息解密或抽取失败 | 整次表达重建回滚，不产生半成品 |
| 应用在重建中退出 | SQLite 事务回滚，下次扫描重新构建 |
| 表达库为空 | 正常不提示，不回退阶段 0 固定文案 |
| 表达删除后重建 | 墓碑优先，表达保持屏蔽 |
| 来源删除导致重复门槛不足 | 下次重建时表达自动移除 |

## 9. 第一版验收

- 两个不同会话使用相同用户句子时生成一个表达；同一会话重复、AI 回复重复均不生效。
- 代码、URL、路径、日志和敏感信息测试集误入为 0。
- 相同历史连续重建三次，表达和来源关系数量不增长。
- 删除表达后立即不再返回，完整重建后仍不返回。
- 删除唯一支撑会话后，表达低于门槛并在重建后消失。
- SQLite、WAL、SHM 和日志中的合成表达明文检出为 0。
- 10 万消息重建在 30 秒内完成；5 万有效表达加载后，前缀检索 p95 小于 10ms，额外常驻内存目标小于 50MB。
- 整个抽取、重建和查询测试在禁网沙箱内通过。
